# Slack sign-in — protocol, deployment and evidence

Recorded: 2026-10-12. **Two genuine Slack identities enrolled TestNet wallets through the unchanged wallet contracts and authorized ALGO and ASA transfers. The node rejected replays and rejected each identity's proof at the other's wallet. Read-only acceptance independently verified all twelve confirmed groups (9/11 checks). Restoring a backup to an existing wallet, and authorizing it with a fresh session, have not been run for Slack. On LocalNet, Slack and Google proofs were each rejected by the other's deployment.**

Slack is a second login provider alongside Google. It reuses the session nonce, identity commitment format, twelve public signals, action signatures and wallet contracts. It has its own circuit, development key and deployment, so neither provider's signing keys or proofs work in the other's wallets.

## How Slack differs from Google

| | Google | Slack |
| --- | --- | --- |
| Issuer | `https://accounts.google.com` (or `accounts.google.com`) | `https://slack.com` |
| Signature | RS256, RSA-2048, e = 65537 | Same; [JWKS](https://slack.com/openid/connect/keys) omits `use` |
| Token delivery | Browser receives it from Google's sign-in library | Authorization code flow; the server exchanges the code with the client secret |
| Token lifetime (`exp − iat`) | Up to 7,200 s accepted | 300 s |
| Signed JSON | Unescaped `/` | Escaped `\/`, e.g. `"https:\/\/slack.com\/team_id"` |
| Wallet subject | `sub` | `team_id/sub` |

Slack's [`openid.connect.token` example](https://docs.slack.dev/reference/methods/openid.connect.token/) suggested the escaped spelling: its truncated token decodes to `.com\/team_i`. A genuine token confirmed it, along with a 300-second lifetime and the claim set below.

## Protocol

**Nonce.** Unchanged: `algorand-zklogin-session-v1` over genesis hash, session public key, expiry and randomness. Slack echoes it in the `nonce` claim.

**Identity commitment.** The same `algorand-zklogin-identity-v1` SHA-256 formula with canonical issuer `https://slack.com`, the Slack client ID as audience, and subject `team_id/sub`. Slack user IDs are workspace-scoped, so the team is part of the wallet identity. Team IDs are constrained to 1–32 visible ASCII bytes without `/`, so the first `/` splits the subject unambiguously. The full subject is at most 255 bytes. Recovery packages use the same format; their encrypted body stores the composite subject.

**Public signals.** The same twelve values in the same order as [Google's](phase3-protocol.md#protocol-v1): identity commitment, RSA modulus SHA-256, audience SHA-256, session key, genesis hash, session expiry and not-before.

**Token profile.** [The Slack circuit](../circuits/slack_jwt.circom) is generated by [`write-jwt-circuit.mjs slack`](../scripts/build/write-jwt-circuit.mjs) from the [profile](../packages/protocol/src/circuit-profile.mjs):

- Header `alg = RS256` and `kid` are required; `typ` is optional and must be `JWT` when present.
- Payload claims are limited to `iss`, `sub`, `aud`, `exp`, `iat`, `auth_time`, `nonce`, `at_hash`, `https://slack.com/team_id`, `https://slack.com/user_id`, `email`, `email_verified`, `date_email_verified` and `locale`. Of these, `iss`, `sub`, `aud`, `nonce`, `iat`, `exp` and team ID are required. Unknown claims are rejected, so the demo requests only the `openid` scope. The `profile` scope adds image-URL claims whose names exceed the 31-byte key limit.
- Claim names are matched in Slack's escaped spelling. `iss` and `email` are kind-3 strings, whose only allowed escape is `\/`. Every other string must contain no backslash. The issuer must be exactly `https:\/\/slack.com`.
- Capacities match Google's: 1,015-byte signed message, 128-byte header and 896-byte payload encodings.

**Time policy.** The circuit requires `iat < session expiry ≤ iat + 600`, `iat < exp`, `exp − iat ≤ 7200` and `iat ≥ 60`, and exposes `notBefore = iat − 60`. Unlike Google's circuit, the session may outlive the token's own `exp`. Slack tokens expire after five minutes, which would otherwise leave too little time for backup and the two-minute local proof. The token is consumed once by the prover, and its nonce binds the browser session key. So the change adds at most about five minutes of key lifetime, still bounded by `iat + 600` and by the contracts' 600-second window. Google's rule is unchanged. The demo checks token validity at login and the session's own expiry thereafter.

## Shared primitives and the Google circuit

[`StrictJsonField`](../circuits/strict_jwt_primitives.circom) now sizes its key window from the allowlist: at least 16 bytes, up to 31, so one field element still holds a packed key. It also has the kind-3 string, whose escape constraints are emitted only when a profile uses it. The Google circuit compiles to the same R1CS: SHA-256 `abed2f1717567ca2d35ac465e2b6e0414b4c3a00cf9b4a1ae334b30078c818fb`, matching [its setup record](../benchmarks/phase3-setup.json). Its proving key, verifier LogicSig and TestNet deployment therefore remain valid.

## Deployment and trust

Each provider has its own deployment of the unchanged contracts:

- a verifier LogicSig derived from that provider's verification key;
- a key registry holding only that provider's signing keys (the `KeyRegistry` contract, formerly `GoogleKeyRegistry`; the rename left its bytecode identical);
- a `WalletRegistry`, and the wallets it creates, pinned to that verifier, key registry and audience at creation.

A Slack proof submitted to a Google wallet or registry fails `Proof verifier required`, and vice versa. A provider's registry approves only keys from that provider's JWKS. Without that separation, whoever holds Slack's signing key could sign a token claiming Google's issuer and arbitrary Google subjects, and Google's circuit would accept it if Slack's key were approved for Google. The LocalNet test shows a Slack proof rejected by a key registry holding only Google's key.

Key-administrator trust is unchanged: the registry creator approves keys fetched over HTTPS from `slack.com`, which the chain cannot authenticate. Slack's client secret stays on the localhost server. That server exchanges the code and sees the ID token, as the local prover already does for Google. With the https relay below, GitHub Pages also receives the authorization code in its request URL; the code needs the client secret to be exchanged.

## Demo login flow

1. The tab opened at `/demo/?provider=slack` creates its non-extractable session key. The server returns the nonce and a Slack authorize URL with `scope=openid`, `nonce` and a random single-use `state`.
2. Sign in with Slack opens a login window, so the tab and its session key stay in place. Slack redirects that window to `SLACK_REDIRECT_URI` or, by default, `http://localhost:8765/demo/slack/callback`.
3. The server matches `state` and exchanges the code at `openid.connect.token` with the client secret. It verifies the ID token against Slack's JWKS, registers Slack keys in the Slack key registry and records the login.
4. The tab polls `/demo/login-status`. Backup, proving, enrollment and transfers then proceed as for Google against the Slack deployment.

**Redirects for PKCE-enabled apps.** Once a Slack app enables PKCE, Slack treats a `localhost` redirect as a desktop redirect and refuses it without PKCE ("Must use PKCE to redirect to a non-web URI"). Two Slack behaviours, recorded on 2026-10-12, made PKCE unusable for Sign in with Slack:

- Slack's `/openid/connect/authorize` redirects to `/oauth/v2/authorize` and drops the PKCE parameters on the way.
- Sending PKCE to `/oauth/v2/authorize` directly reaches consent, but `openid.connect.token` then answered `internal_error`, both with and without the client secret.

The demo therefore uses an https redirect: a static relay page, [`apps/oauth-relay`](../apps/oauth-relay/index.html), published at `https://bwmx.github.io/algo-zkauth/slack-callback/` from the `gh-pages` branch. Register that URL in the Slack app, set it as `SLACK_REDIRECT_URI`, and the documented secret-based flow applies. The relay forwards only `code`, `state` and `error` to the fixed localhost callback, removes them from the address bar and sends no referrer. With a non-https redirect the code still sends PKCE, for apps where Slack accepts it.

## Measurements and evidence

| Measurement | Slack | Google (Phase 3) |
| --- | ---: | ---: |
| Constraints | 2,563,372 (2,229,792 nonlinear) | 2,726,377 |
| Wires | 2,489,556 | 2,648,553 |
| Development proving key | 1,360,364,984 bytes | 1,425,797,992 bytes |
| Circuit-specific setup | 541.5 s; 5.29 GB sampled peak RSS | 660.8 s; 3.16 GB |

[Setup evidence](../benchmarks/slack-setup.json) records the R1CS/zkey hashes and the same power-22 file. This is a **development setup, not a production ceremony**.

**Genuine Slack token.** [`check-login.mjs slack`](../evidence/login/check-login.mjs) (then `check-slack-login.mjs`) signed in once through the relay. It bound a random session key whose private half is never kept, so the token can authorize nothing. [The sanitized record](../benchmarks/slack-token-profile.json) holds names, lengths and outcomes only:

- header `alg`, `typ` (`JWT`) and `kid`;
- exactly the ten `openid` claims (`iss`, `sub`, `aud`, `exp`, `iat`, `auth_time`, `nonce`, `at_hash`, team ID, user ID), all inside the profile;
- escaped `\/` throughout, matching the circuit's expected spelling byte for byte;
- a 538-byte signed message and a 323-byte decoded payload (limits 1,015 and 672);
- a 300-second lifetime.

Slack-signature verification, circuit preflight and the full circuit witness passed. [`prove-login.mjs slack`](../evidence/login/prove-login.mjs) then generated a Groth16 proof offline from the saved token in 120.8 s (2,325 MB sampled peak RSS) and verified it against the Slack verification key.

[Five witness tests](../tests/circuits/slack-circuit-witness.test.mjs) cover:

- the full and minimal openid claim sets;
- off-chain preflight;
- correctly signed tokens with Google's issuer, the unescaped or `/` issuer spelling, a missing team, a team containing `/`, an unknown claim, a backslash in a plain string, `typ` other than `JWT`, and a session longer than `iat + 600`;
- identity preimages that drop or reorder the team.

Each rejection was traced to its intended constraint. [Unit tests](../tests/unit/slack-id-token.test.mjs) cover token verification, the [code exchange](../tests/unit/code-login.test.mjs), sessions and the Slack page flow under stubs.

**LocalNet run.** [`run-provider-localnet.sh slack`](../tests/localnet/run-provider-localnet.sh) (then `run-slack-localnet.sh`) proved one synthetic Slack identity in 124.5 s: witness 2.7 s, 1,886 MB sampled peak RSS, Node v24.15.0 on macOS/arm64 ([proof record](../benchmarks/slack-proofs.localnet.json)). It then passed six checks ([wallet record](../benchmarks/slack-wallets.localnet.json)):

- each provider's proof was rejected by the other's deployment with `Proof verifier required`;
- the Slack proof was rejected by a key registry holding only Google's key, with `Google key inactive` (now `Key inactive`);
- a wallet was enrolled, bound to the Slack verifier and key registry;
- an exact ALGO transfer was authorized;
- replay of that transfer was rejected with `Wrong action nonce`.

Rejections were checked through simulation messages and node submission. Enrollment and transfer each used seven outer transactions, a 0.02 ALGO group fee, 78,378 LogicSig opcodes and 3,174 / 2,967 app opcodes, the same as Google's groups. The record includes the contract source hashes; the contracts are unchanged.

**TestNet run.** The Slack deployment is registry `774125501`, key registry `774125499` and demo ASA `774125516`, approving the Slack key that signed the genuine token ([deployment record](../benchmarks/slack-deployment.testnet.json)). In the first run, a browser session as Account C ran the demo at `/demo/?provider=slack`:

- signed in through the relay;
- created and secret-restored a backup;
- proved locally in 124.0 s (121.2 s proving, 1.89 GiB sampled peak Node RSS);
- enrolled wallet `774125965` (`KT3O3WGMWX7BSXZAIDO7US7GXKW3D2PRLIGBM3XQINSP7OHMVUVYC57LGU`);
- sent 0.01 ALGO, opted into and received the demo ASA, and sent 7 units back;
- confirmed in rounds 68190981–68190996; the node then rejected a replay at the nonce check.

A second Slack identity, Account D, then ran the same sequence in a separate browser context and enrolled wallet `774127169`. Its run presented D's proof to Account C's wallet, and the node rejected it at the owner check, leaving C's nonce and balance unchanged. A later Account C session restored a backup with a different salt. That run therefore enrolled a second C wallet, `774127414`, and its run was likewise rejected at D's wallet. One Slack identity can hold several wallets, one per salt.

[`check-demo.sh slack`](../evidence/check-demo.sh) verifies every wallet of each account separately and passed 9 of 11 checks ([acceptance record](../benchmarks/slack-acceptance.testnet.json)). From historical blocks, for all twelve confirmed groups across the three wallets, it checked:

- the group's seven transactions and the Slack verifier sender;
- the reverified proof and the browser action signature;
- inner transfers, fees, nonces and balances.

Each wallet ends at nonce 3, 1,090,000 µALGO and 93 ASA units. Each group used seven outer transactions, a 0.02 ALGO fee and 78,378 LogicSig opcodes, plus 3,174 app opcodes for enrollment and 2,967–2,979 for execution. That matches Google. The two pending checks need a run that restores a backup to an existing wallet and transfers with a fresh session. A later attempt was correctly refused ("Sign in to the original Slack identity to restore") because the browser's Slack session was Account D, and the test was then deferred. Session and identity labels come from the local server records, as for Google.

## Not yet verified

- Slack backup restore to an existing wallet followed by a transfer, and a fresh Slack session authorizing an existing wallet. These are the two pending acceptance checks. To run them, sign in as the wallet's own Slack identity, restore that identity's backup without creating a new salt, prove, and send a transfer.
- Disposable key/session-policy checks for the Slack registry. These are listed as deferred.
- Other Slack accounts and workspaces, notably Enterprise Grid, whose IDs or claims may differ. If a token falls outside the profile, preflight reports a profile error before proving. Fixing it means updating the Slack entry of `CIRCUIT_PROFILES` or the escaping, regenerating the circuit, rerunning setup and redeploying.
- Sign in with Slack for a PKCE-enabled app without the https relay, given Slack's PKCE behaviour above.
- Everything open for Google also applies: audit, production setup, browser proving and key governance.
