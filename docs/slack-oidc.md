# Slack sign-in — protocol, deployment and evidence

Recorded: 2026-10-12. **A synthetic Slack-shaped token enrolled a wallet and authorized an ALGO transfer on LocalNet through the unchanged wallet contracts, and cross-provider proofs were rejected. A genuine Slack login has not been exercised; the circuit's Slack token profile is inferred from Slack's documentation and must be confirmed with a real token.**

Slack is a second login provider alongside Google. It reuses the session nonce, identity commitment format, twelve public signals, action signatures and wallet contracts. It has its own circuit, development key and deployment, so neither provider's signing keys or proofs work in the other's wallets.

## How Slack differs from Google

| | Google | Slack |
| --- | --- | --- |
| Issuer | `https://accounts.google.com` (or `accounts.google.com`) | `https://slack.com` |
| Signature | RS256, RSA-2048, e = 65537 | Same; [JWKS](https://slack.com/openid/connect/keys) omits `use` |
| Token delivery | Browser receives it from Google's sign-in library | Authorization code flow; the server exchanges the code with the client secret |
| Token lifetime (`exp − iat`) | Up to 7,200 s accepted | 300 s in Slack's examples |
| Signed JSON | Unescaped `/` | Escaped `\/`, e.g. `"https:\/\/slack.com\/team_id"` |
| Wallet subject | `sub` | `team_id/sub` |

The escaped spelling comes from Slack's [`openid.connect.token` example](https://docs.slack.dev/reference/methods/openid.connect.token/): its truncated token decodes to `.com\/team_i`.

## Protocol

**Nonce.** Unchanged: `algorand-zklogin-session-v1` over genesis hash, session public key, expiry and randomness. Slack echoes it in the `nonce` claim.

**Identity commitment.** The same `algorand-zklogin-identity-v1` SHA-256 formula with canonical issuer `https://slack.com`, the Slack client ID as audience, and subject `team_id/sub`. Slack user IDs are workspace-scoped, so the team is part of the wallet identity. Team IDs are constrained to 1–32 visible ASCII bytes without `/`, so the first `/` splits the subject unambiguously. The full subject is at most 255 bytes. Recovery packages use the same format; their encrypted body stores the composite subject.

**Public signals.** The same twelve values in the same order as [Google's](phase3-protocol.md#protocol-v1): identity commitment, RSA modulus SHA-256, audience SHA-256, session key, genesis hash, session expiry and not-before.

**Token profile.** [The Slack circuit](../circuits/slack_jwt.circom) is generated by [`write-slack-circuit.mjs`](../scripts/write-slack-circuit.mjs) from the [profile](../src/phase3/circuit-profile.mjs):

- Header `alg = RS256` and `kid` are required; `typ` is optional and must be `JWT` when present.
- Payload claims are limited to `iss`, `sub`, `aud`, `exp`, `iat`, `auth_time`, `nonce`, `at_hash`, `https://slack.com/team_id`, `https://slack.com/user_id`, `email`, `email_verified`, `date_email_verified` and `locale`. Of these, `iss`, `sub`, `aud`, `nonce`, `iat`, `exp` and team ID are required. Unknown claims are rejected, so the demo requests only the `openid` scope. The `profile` scope adds image-URL claims whose names exceed the 31-byte key limit.
- Claim names are matched in Slack's escaped spelling. `iss` and `email` are kind-3 strings, whose only allowed escape is `\/`. Every other string must contain no backslash. The issuer must be exactly `https:\/\/slack.com`.
- Capacities match Google's: 1,015-byte signed message, 128-byte header and 896-byte payload encodings.

**Time policy.** The circuit requires `iat < session expiry ≤ iat + 600`, `iat < exp`, `exp − iat ≤ 7200` and `iat ≥ 60`, and exposes `notBefore = iat − 60`. Unlike Google's circuit, the session may outlive the token's own `exp`. Slack tokens expire after five minutes, which would otherwise leave too little time for backup and the two-minute local proof. The token is consumed once by the prover, and its nonce binds the browser session key. So the change adds at most about five minutes of key lifetime, still bounded by `iat + 600` and by the contracts' 600-second window. Google's rule is unchanged. The demo checks token validity at login and the session's own expiry thereafter.

## Shared primitives and the Google circuit

[`StrictJsonField`](../circuits/strict_jwt_primitives.circom) now sizes its key window from the allowlist: at least 16 bytes, up to 31, so one field element still holds a packed key. It also has the kind-3 string, whose escape constraints are emitted only when a profile uses it. The Google circuit compiles to the same R1CS: SHA-256 `abed2f1717567ca2d35ac465e2b6e0414b4c3a00cf9b4a1ae334b30078c818fb`, matching [its setup record](../benchmarks/phase3-setup.json). Its proving key, verifier LogicSig and TestNet deployment therefore remain valid.

## Deployment and trust

Each provider has its own deployment of the unchanged contracts:

- a verifier LogicSig derived from that provider's verification key;
- a key registry holding only that provider's signing keys (the `GoogleKeyRegistry` contract, unrenamed so its bytecode stays identical);
- a `WalletRegistry`, and the wallets it creates, pinned to that verifier, key registry and audience at creation.

A Slack proof submitted to a Google wallet or registry fails `Proof verifier required`, and vice versa. A provider's registry approves only keys from that provider's JWKS. Without that separation, whoever holds Slack's signing key could sign a token claiming Google's issuer and arbitrary Google subjects, and Google's circuit would accept it if Slack's key were approved for Google. The LocalNet test shows a Slack proof rejected by a key registry holding only Google's key.

Key-administrator trust is unchanged: the registry creator approves keys fetched over HTTPS from `slack.com`, which the chain cannot authenticate. Slack's client secret stays on the localhost server. That server exchanges the code and sees the ID token, as the local prover already does for Google.

## Demo login flow

1. The tab opened at `/demo/?provider=slack` creates its non-extractable session key. The server returns the nonce and a Slack authorize URL with `scope=openid`, `nonce` and a random single-use `state`.
2. Sign in with Slack opens a login window, so the tab and its session key stay in place. Slack redirects that window to `http://localhost:8765/demo/slack/callback`.
3. The server matches `state` and exchanges the code at `openid.connect.token` with the client secret. It verifies the ID token against Slack's JWKS, registers Slack keys in the Slack key registry and records the login.
4. The tab polls `/demo/login-status`. Backup, proving, enrollment and transfers then proceed as for Google against the Slack deployment.

The code exchange uses the client secret, not PKCE. Slack's discovery document advertises only secret-based token authentication.

## Measurements and evidence

| Measurement | Slack | Google (Phase 3) |
| --- | ---: | ---: |
| Constraints | 2,563,372 (2,229,792 nonlinear) | 2,726,377 |
| Wires | 2,489,556 | 2,648,553 |
| Development proving key | 1,360,364,984 bytes | 1,425,797,992 bytes |
| Circuit-specific setup | 541.5 s; 5.29 GB sampled peak RSS | 660.8 s; 3.16 GB |

[Setup evidence](../benchmarks/slack-setup.json) records the R1CS/zkey hashes and the same power-22 file. This is a **development setup, not a production ceremony**.

[Five witness tests](../tests/slack-circuit-witness.test.mjs) cover:

- the full and minimal openid claim sets;
- off-chain preflight;
- correctly signed tokens with Google's issuer, the unescaped or `/` issuer spelling, a missing team, a team containing `/`, an unknown claim, a backslash in a plain string, `typ` other than `JWT`, and a session longer than `iat + 600`;
- identity preimages that drop or reorder the team.

Each rejection was traced to its intended constraint. [Unit tests](../tests/slack-id-token.test.mjs) cover token verification, the [code exchange](../tests/slack-login.test.mjs), sessions and the Slack page flow under stubs.

**LocalNet run.** [`run-slack-localnet.sh`](../scripts/run-slack-localnet.sh) proved one synthetic Slack identity in 124.5 s: witness 2.7 s, 1,886 MB sampled peak RSS, Node v24.15.0 on macOS/arm64 ([proof record](../benchmarks/slack-proofs.localnet.json)). It then passed six checks ([wallet record](../benchmarks/slack-wallets.localnet.json)):

- each provider's proof was rejected by the other's deployment with `Proof verifier required`;
- the Slack proof was rejected by a key registry holding only Google's key, with `Google key inactive`;
- a wallet was enrolled, bound to the Slack verifier and key registry;
- an exact ALGO transfer was authorized;
- replay of that transfer was rejected with `Wrong action nonce`.

Rejections were checked through simulation messages and node submission. Enrollment and transfer each used seven outer transactions, a 0.02 ALGO group fee, 78,378 LogicSig opcodes and 3,174 / 2,967 app opcodes, the same as Google's groups. The record includes the contract source hashes; the contracts are unchanged.

## Not yet verified

- **A genuine Slack ID token.** The escaped spelling, the exact `openid` claim set, the `typ` header and the five-minute lifetime come from Slack's documentation. If a real token differs, preflight reports a profile error before proving. Update `SLACK_PAYLOAD_KEYS` or the escaping, regenerate the circuit and setup, and redeploy.
- Whether Slack accepts the `http://localhost` redirect URL. Slack's documentation is inconsistent.
- A TestNet Slack deployment and genuine demo run. [`check-demo.sh`](../scripts/check-demo.sh) checks the Google deployment only.
- Everything open for Google also applies: audit, production setup, browser proving and key governance.
